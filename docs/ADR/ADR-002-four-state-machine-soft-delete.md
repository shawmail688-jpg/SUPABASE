# ADR-002：四态状态机 + 审批流 + 全库软删除

Status：Accepted
Date：2026-09-03
决策者：用户（v1.3 第三轮 #3/#4/#5 定案）
来源：Proposal v1.3 §8.2/§8.4

# 一、背景（Context）

- v1.2 曾有九态设计，领导与用户沟通后简化：调查员只产「调查中」，批准才候选、再批才已选
- 「删除」需求实为「否决/剔除」：数据一条不能真删（十几人团队误删无恢复、无留痕不可接受）
- 未来「在营」状态需要总部经营数据自动点亮，现在没有数据源

# 二、决策（Decision）

- 状态四态：`surveying → candidate → selected → archived`；`operating` 枚举预留不启用
- 提交即调查中（系统自动）；→candidate/→selected 仅管理层批准；→archived（隐藏=否决）管理层；恢复仅 admin
- 每次状态变更写 `site_status_log`（who/when/from/to/action/note）
- **全库软删除**：数据库层无物理 DELETE 授权，任何删除路径走 status

# 三、候选方案与取舍（Alternatives）

| 方案 | 理由 | 否决原因 |
|------|------|----------|
| **四态+审批流** ✅ | 与实际管理动作一一对应；比九态更简 | — |
| v1.2 九态 | 状态粒度细 | 十几人规模用不上，维护成本高 |
| 物理删除+回收站 | 熟悉范式 | 云 DB 上误删恢复靠人肉；软删除+RLS 拒 DELETE 更硬 |
| 在营状态立即启用 | 语义完整 | 无总部数据源，枚举空转；预留即可 |

# 四、验证证据（如经评估 / 原型）

- 状态机合法性将在 M1 以转换矩阵用例机器验证（6 合法路径过/非法路径拒）——待实现
- 语义一致性：隐藏=软删除=否决三处同语义（§8.2/§8.4/看板按钮）

# 五、后果（Consequences）

- 正面：审批责任全程可追溯；误操作可恢复；状态口径唯一（site_status_log 为权威）
- 代价 / 技术债：archived 数据永远占库（十几人规模无压力）；调查员 UI 需正确处理「隐藏后不可见」
- 回退触发条件：管理层反馈状态不够用（如需要「复核中」）→ 走 C2 变更路径加态，不改已有语义
