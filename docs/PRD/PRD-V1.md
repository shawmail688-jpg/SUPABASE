# 一、背景

## 1.1 当前问题

| 现状 | 问题 |
|------|------|
| 调查数据存 Google Sheet 双表，链接共享即全可见 | **安全债**：租金/联系人裸奔，无鉴权粒度，无操作留痕 |
| 照片存本地文件夹，Atlas 靠本机隧道（atlas_bridge）对外 | **单点**：办公室机器关机=看板哑；换设备调阅难 |
| 「删除」= 删 Sheet 行 / 删文件 | 无软删除语义，误删无恢复，无 who/when |
| 状态靠口头/群聊沟通 | 谁批的、何时批的、从什么状态到什么状态，无记录 |
| 领导只能看静态导出的 Atlas 页 | 手机体验弱、无审批动作、无筛选 |

## 1.2 为什么不做替代品

- **不上 ERP/门店系统**：公司已有系统管经营数据；本平台只管自己产生的数据（选址调查/店面基本信息），边界见 Proposal §1 数据归属表
- **不留在 Google Sheet**：无鉴权粒度、链接共享裸奔、天花板低——正是要还的债（Proposal §5 判定）
- **不自建视频/服务器**：监控走厂商云（后续项目）、数据库走 Supabase 托管，十几人团队不养运维

# 二、产品定位

- **V1（本版）**：店面数据系统 MVP——照片上云多端可调、四态审批状态机、双视图看板（领导手机视图+管理层桌面工作视图）、存量数据/照片迁移
- **V2+（后续项目，不在本版）**：监控影像嵌入（厂商开放平台轨道）、总部经营数据 API 接入（归档轨道）
- **核心闭环**：调查员提交（在线直传/离线攒单）→ DB 唯一权威 → 管理层批准 → 候选/已选 → 领导手机地图看全貌；隐藏=否决可恢复，全程留痕
- **复现闭环**：换 project + domain_config 配置 = 换电站系统，代码零改（本版建轴不扩展）

# 四、功能设计

## 4.1 视图关系与信息架构（用户 09-03 确认的理解）

**两个视图 = 同一个 Supabase DB 的两个前端，不是两份数据。**

```
                 ┌─ 领导视图 /leader（手机，看+批）──┐
Supabase DB ─────┤                                  ├─ 管理层登录后可互切
（唯一权威）      └─ 工作视图 /work（桌面，查改批藏导出）┘
```

- **切换**：登录后导航互切；管理层（用户+领导）两个视图都可进；调查员无看板入口（RLS 拦 + UI 不渲染）
- **一致性承诺**：任一视图的写操作（批准/隐藏/编辑）落 DB 后，另一视图**刷新即最新**——不存在「两边不一样」；**调查提交 Realtime 推送为阶段一基线**（沿用 Proposal 附录 A 第一轮 #8 采纳项：调查提交→看板自动冒新 pin）；全事件实时刷新（编辑/批准/隐藏的自动推送）为增强项，架构阶段定档
- **反向**：调查员野外提交 → 工作视图立即可见（刷新后）

## 4.2 数据层与状态机（R1-R5, R8, R17）

### 规则（规则优先于界面）

| 规则 | 内容 |
|------|------|
| 表清单 | project / domain_config / app_user / site / survey_result / photo / site_status_log / external_ids / audit_log / fengshui_eval；**device 不建**（随 M5） |
| site≠survey | 一个 site 可挂多次 survey_result，历次全保留永不覆盖 |
| 状态 | surveying → candidate → selected → archived；`hidden` 为拒绝/隐藏态，operating 枚举预留不启用 |
| 提交即调查中 | 调查员首次提交某 site → 系统自动置 surveying（系统判的） |
| 批准链 | surveying→candidate、candidate→selected **仅管理层**；调查员永远碰不到 candidate |
| 隐藏 | surveying/candidate/selected/archived → hidden = 否决（管理层）；数据一条不删，默认列表过滤 hidden |
| 恢复 | hidden → 原状态，**仅 admin**；「原状态」取该 site **最后一条 to_status='hidden' 的 site_status_log 行的 from_status**（无则回 surveying） |
| 留痕 | 每次状态变更写 site_status_log（who/when/from/to/action/note）；关键表变更触发 audit_log（old→new） |
| 软删除 | 全库无物理 DELETE 授权（RLS 层拒绝），任何删除路径走 status |
| 角色 | **管理层**=用户+领导同权（全量读写+批准+隐藏）；**恢复=仅 admin**（与 R2/Proposal §8.4 一致；R4 原文「隐藏/恢复」为简写，勘误对齐）；**调查员**=仅 INSERT/UPDATE 自己的数据；**anon=零** |
| 复现轴 | 调查字段结构存 domain_config；数据按 project 隔离（RLS），看板按 project 切换 |

### 状态机图

```
调查员提交 ──→ 调查中 ──管理层批准──→ 候选 ──管理层批准──→ 已选
  (surveying)    │                  │                  │
                 └────── 隐藏（hidden，可恢复，仅 admin 恢复）──┘
                 在营（operating）：枚举预留，暂不启用
```

## 4.3 照片上云（R9-R12）

| 规则 | 内容 |
|------|------|
| 存储 | Storage 私有桶，短时效签名 URL 读取；无任何公开链接路径 |
| 压缩 | 拍摄→**设备本地**压缩→直传：默认档长边 1600-2000px / JPEG ~80%；「细节照」开关走高质量档（合同小字/车牌场景） |
| 失败 | 上传失败进离线队列自动重试（离线灵魂不砍） |
| 存量 | 本地既有照片一次性迁入 Storage+登记 photo 表（sha1 去重）——用户 09-03 裁定迁入 |
| 换靶 | 在线直传换靶平台 API；离线队列逻辑原样；Apps Script 旧通道双写 ≥7 天对账零差异后退役 |

## 4.4 看板（R13-R16）

### 领导视图（手机优先，单页三层）

```
┌──────────────────────────┐
│ 调查中 3 · 候选 5 · 已选 2 │ ← 顶部汇总条，数字即筛选（点击列出对应店）
├──────────────────────────┤
│      地图（pin 按状态着色） │ ← 点 pin 底部弹出店面卡：
│   ●●●  ○○    ▲            │   照片轮播/名称/区域/状态/面积/租金/最近调查
├──────────────────────────┤
│ [地图|列表]  区域▾          │ ← 双模式切换 + 区域筛选
└──────────────────────────┘
```

# 十一、成功标准与失败信号

**成功标准（行为改变，可衡量）**：
1. 领导在手机上**独立完成**一次「看地图→点开店面→批准为候选」全流程，无需他人协助（M3a 验收核心）
2. 任何一台设备（电脑/手机）能调阅全部店面照片，包括存量照片（M2a 验收核心）
3. 调查员在断网野外照常交表，回网自动同步零丢失（离线灵魂保持）
4. 每次批准/隐藏都能回答「谁、何时、从哪状态到哪状态」（留痕闭环）
5. 用户与领导对界面观感的实开验收通过（N5）

**失败信号（触发反思/砍功能）**：
1. 双写对账连续 3 天非零差异且无法归因 → 暂停换靶，回退 S4，排查后再排期
2. 领导实开验收两次不过 → 暂停推进，回到看板设计（§4.1）重新过用户
3. 照片压缩后仍超流量预期（月 Storage/流量费明显超 $25 套餐常轨）→ 重审压缩档参数
4. 工作视图某操作 E2E 连续两轮修不过 → 记技术债（C4）+评估 Fable 备胎触发条件 ①
