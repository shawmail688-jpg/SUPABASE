## 0. 一页纸摘要（给领导 30 秒版）

**定位**：给乌干达分部十几个人用的**小型店面数据系统**——店面位置、选址调查、店面基本信息由我们自己采集管理；**实时监控影像嵌在页面里直接看**（走摄像头厂商云，不自建视频系统）；经营数据未来若需要，调总部 API 展示（接口已归档预留，§11）。整套跑通后换配置复用到换电站项目。

**阶段一（约 7 个工作日）**：照片全部上云入库、每台设备随时调阅、领导手机看地图+照片+审批。**底座**：Supabase 付费档（$25/月），选址调查与店面管理两个系统共用这一个库，库是承重墙不是实验田。

**年成本**：**≈$360/年（≈¥2,600）** = Supabase Pro $25/月×12 + AI 开发工具备胎 $20/月×3（启用待定）+ 域名 ¥70/年（§6）。上线后常态 $25/月。

**原则**：不重复造轮子。监控画面走厂商已有的云能力，我们只做台账和嵌入播放；总部已有的经营数据以总部为唯一数据源（轨道已归档，触发即恢复）。

## 1. 系统边界与数据归属（置于一切架构之前）

**一句话定位**：本平台不是公司 ERP/CRM/POS/门店管理/IoT 的替代品，也不是它们的重建版。它是乌干达分部的数据与展示前台：自己产生的数据自己管，别家已有的能力直接用。

| 数据 | 权威方 | 本平台角色 |
|------|--------|-----------|
| 选址调查记录、候选点位、调查照片 | **本平台** | 唯一采集与管理者 |
| 店面基本信息（名称/地址/面积/负责人） | **本平台** | 采集与管理（若总部已有门店主数据，以调查结果定同步关系） |
| **监控画面/摄像头设备** | **摄像头厂商云**（海康/大华系开放平台） | **台账（设备信息入库）+ 嵌入播放（画面长在页面里，不自建视频链路）** |
| 经营数据（销售/库存/收款） | 总部系统 | **归档暂不接入**（§11，触发即恢复；只读展示，不二次维护） |
| 财务数据 | 总部财务系统 | 不接入（超出本平台范围） |

**归属原则**：本平台只对自己产生的数据承担权威责任；对厂商云与总部系统已有的能力/数据，不重复建设、不二次维护、不建立第二套事实源。

## 4. 总体架构

```
┌─ 摄像头厂商云（新增链路）────────────────────────────────────┐
│ 海康/大华系开放平台（画面与设备的权威方，带宽与视频基础设施归它）│
└───────────────┬──────────────────────────────────────────────┘
                │ 开放平台 API（appKey/secret 服务端保管）
                ▼
┌─ 安全接口层（Supabase Edge Function 代理）─────────────────┐
│ 第三方凭证保管（服务端密钥）· 一次性播放地址（短时效 token） │
│ 白名单（仅本平台登记设备）· 调用留痕                        │
│ 〔归档轨道：总部 API 同走此层，触发即恢复，§11〕             │
└──────┬───────────────────────────────┬────────────────────┘
       │ 监控：页面内嵌厂商 H5 播放器    │ 归档轨道：实时透传/落库过映射（§8.3）
       ▼                               ▼
┌─ 平台数据层（Supabase Pro）────────────────────────────────┐
│ Postgres(+PostGIS)：site/survey_result/photo/device/       │
│   external_ids/site_status_log/audit_log…（软删除+四态）   │
│ Auth：一人一号（admin 建号）  RLS：行级权限（§8.4 两类角色）│
│ Storage：照片私有桶+签名 URL   Realtime：调查提交实时推送   │
└────┬──────────────────────────────┬────────────────────────┘
     │ 〔归档备轨：投影/写回，§9〕    │ REST
     ▼                              ▼
┌─ Google Sheets（历史数据存档）──┐  ┌─ 前端 ──────────────────┐
│ M4 工作台化已取消（09-03）；    │  │ 调查表单（离线+在线直传+ │
│ 三条同步规则留作备轨            │  │ 拍照压缩直传）           │
└───────────────────────────────┘  │ 看板：领导视图+工作视图   │
                                   │ （Atlas 骨架迁移，§4.1）  │
                                   └─────────────────────────┘
```

**六条关键设计决策**：
1. **Postgres 为权威底座，Sheets 为工作台**——DB 管「真」，Sheet 管「顺手」；有一天 Sheet 不用了，只是换管理前端，数据库与表单零推倒（§9）。
2. **表单离线模式原样保留**——在线直传换靶平台 API，离线攒单回网同步逻辑不动。
3. **照片：拍摄→本地压缩→直传 Storage**。默认档 1600-2000px、JPEG 质量 ~80%、单张 300KB-1MB——门头/道路/周边环境照肉眼无损；**「细节照」开关走高质量档**（合同小字/车牌/仪表场景不压狠）。压缩在调查员设备本地完成：省流量、弱网上传快、失败走离线队列自动重试。本地原图归档降级为现有管线的既有行为，**平台不依赖它**。
4. **监控不自建视频链路**（§4.2）：画面走厂商云，平台只做台账+嵌入播放；第三方凭证与总部凭证同纪律，永远不进前端。
5. **外部数据二分**（§8.3，归档轨道预置）：实时展示走代理透传不落库；只有需要快照/历史的落库数据才过 external_ids 映射。总部业务表结构**不预建**。
6. **配置驱动支持复现**：调查字段结构存 `domain_config`，换电站=第二份配置，不换代码。

### 4.1 看板设计（阶段一只交付领导视图）

**领导视图（手机优先）**——单页三层：

1. **顶部汇总条**：打开第一眼是数字不是地图——调查中 X · 候选 X · 已选 X，三个数字**本身就是筛选项**，点了列出对应店；状态色块与地图 pin 同色。在营状态预留位不显示（§8.4）
2. **主区地图**：坎帕拉底图，pin 按状态着色；点 pin 底部弹出店面卡（照片轮播、名称、区域、状态、面积/租金、最近调查日期）——**弹窗卡片+照片灯箱复用 Atlas T22 已验收骨架**，只换数据源
3. **详情页**：基础信息全量 + 照片墙 + 调查记录时间线 + 状态变更日志（谁在何时批的/藏的）；**「批准为候选」「隐藏」两个按钮**（仅管理层可见，RLS 校验）

筛选项另加「区域」；「地图/列表」双模式切换，列表为卡片流，照顾不习惯地图的人。技术：领导账号走 Auth+RLS，页面仅两个写操作（批准/隐藏），不碰表单不碰 Sheets；cloudflared 兜底。

**工作视图（桌面，管理层日常用）**——阶段二交付：店面表格（名称/区域/状态/最近更新/调查次数）+ 详情页字段全量 + 调查时间线 +（M5 后）监控区块 + 待调查/待复核清单 + **归档恢复入口（仅 admin）**。

### 4.2 监控影像接入方案（厂商开放平台轨道）

**定位**：画面**长在平台页面里**（内嵌厂商 H5 播放组件），不是跳转外链。不自建视频链路：媒体服务器、公网带宽、视频安全面全归厂商，平台只管凭证、台账和权限。

**链路**：摄像头 → 厂商云 → Edge Function（保管 appKey/secret，按设备取**一次性播放地址**，短时效 token 不落库）→ 页面内嵌播放器。带宽按观看人数走厂商云，平台侧零视频流量成本。

**两道前置闸门（本地 IT 盘点定，§11）**：
1. **品牌/云能力**：海康/大华系有云能力的店走嵌入；杂牌店二选一——**加装一台云摄像头（¥200-500/台，最便宜）**或自建中继（归档备胎，见下）
2. **开放平台国际区可用性**：国内版/国际版账号体系常不通用，乌干达设备绑哪个区需实测（厂商渠道商一句话确认）

| 档 | 适用 | 一次性 | 月费 |
|----|------|--------|------|
| A 厂商开放平台 | 有云能力的摄像头 | M5b 开发 2-4 天 | 免费额度内 ¥0；超出约 ¥3-10/路/月（**待核实**，品牌定后按价目表填） |
| B 杂牌店加装 | 无云能力杂牌 | ¥200-500/台 × 杂牌店数 | 同 A |
| C 自建中继（**归档备胎，默认不启动**） | 无云能力且必须看 | 开发 3-5 天 | 服务器 $10-20/月+带宽 $20-50/月，维护重 |

**安全咬合（三处现成接口）**：厂商 appKey/secret 进 Edge Function 服务端（与 §7 第五层同纪律）；摄像头设备 ID 进 `external_ids`（entity_type='device'，§8.3 本就在表结构里）；谁能看哪家店的监控走 RLS 与照片同逻辑。

## 7. 安全模型

**正式声明（写入系统设计的硬约束）**：
> 所有业务数据以 Supabase PostgreSQL 为线上正式数据源，通过 Supabase Auth + RLS 实现用户身份认证和数据访问控制；Storage 中的调查照片默认不公开。**任何第三方系统（摄像头厂商开放平台、总部系统）的调用均不得将其凭证暴露给客户端**，必须通过受控的服务端接口完成，并遵循最小权限原则。

**五层落地**：

| 层 | 措施 |
|----|------|
| ① 账号认证 | 一人一号，**不共用账号**；admin（用户本人）在 Supabase Auth 创建/停用所有人账号。谁提交、谁审批、谁隐藏全程可追溯 |
| ② 权限控制（v1.3 定案） | Postgres RLS 两类角色：**管理层**（用户+领导账号，同权）= 全量读写 + 审批 + 隐藏/恢复；**调查员** = 仅 INSERT/UPDATE 自己提交的数据、不可 DELETE、**不可改 status**；匿名零权限（纠正现状 anon 可读姿态） |

| ④ 平台密钥 | `secret key` 与第三方凭证（厂商 appKey/secret、未来的总部凭证）**只存在于服务端**（Edge Function/worker），前端只见 publishable key+RLS 兜底 |

审计：`audit_log` 表+触发器（who/when/old→new）+ `site_status_log` 状态流水（§8.4）；备份：Supabase 自动快照+PITR，另加每日 pg_dump 本地冷备（双保险），恢复步骤写 runbook。

### 8.4 状态机与审批流（v1.3 定稿）

```
调查员提交 ──→ 调查中 ──领导批准──→ 候选 ──领导批准──→ 已选
  (surveying)    │                 │                 │
                 └───────── 隐藏（archived，软删除，可恢复）──┘
                 在营（operating）：枚举预留，暂不启用
```

| 转换 | 谁触发 | 落库 |
|------|--------|------|
| 提交调查表 → 调查中 | **系统自动**（调查员首次提交该 site 即生成，状态即调查中） | created_by / created_at |
| 调查中 → 候选 | **管理层批准按钮**（看板领导视图） | site_status_log：谁/何时/从哪到哪 |
| 候选 → 已选 | **管理层批准按钮** | 同上 |
| 调查中/候选/已选 → 隐藏 | 管理层（**隐藏=否决**：调查中否决、候选落选、已选剔除） | 同上 |
| 隐藏 → 恢复 | 仅 admin（工作视图恢复入口） | 同上 |

**判定规则**：调查中是系统判的（提交即调查中）；候选与已选是批出来的（调查员权限到调查中为止，永远碰不到候选）；在营预留位未来由总部经营数据自动点亮（归档轨道恢复时的第一个应用）。隐藏后数据一条不删：默认列表全滤掉、admin 可见可恢复。

## 9. Google Sheets：历史存档 + 归档备轨（09-03 修订：工作台化取消）

**修订理由**：审批/隐藏/编辑/导出全部由网页（工作视图+领导视图）承接后，双向同步这个全方案最易出 bug 的组件失去了存在理由；用户作为主要操作者选择网页。Sheets 转为历史数据存档（迁移完成即冻结），数据直看两路：**工作视图**（日常查/改/批/藏/导出）+ **Supabase Studio 表编辑器**（admin 应急直查，零开发）。若未来仍想要 Sheet 投影，备轨随时可捡：按下列三条规则实现，约 2 天（原 M4 方案）。

**三条规则（归档备轨，重启时生效）**：
1. **删行允许，归档在 DB**。Sheet 里照常删行；同步引擎按 ID 列对账（DB 有、Sheet 无）→ 该行 `status='archived'`。物理删除只发生在 Sheet 视图层，数据库永远软删。事实注记：Apps Script 行删除事件不带操作人，删行路径的归档记录缺「谁删的」；需要留人时改用状态列改「停用」（who/when 全留）。两种操作都合法，按习惯选。
2. **ID 列作同步键**。DB→Sheet 投影与 Sheet→DB 写回都按本平台 ID 列对应，**永不按行号**。
3. **行级 last-write-wins**：两端改同一行时，整行按 `updated_at` 裁决，新者入库，败者完整存入 audit_log。**字段级冲突裁决明确不做**——十几人规模，那是花实现精力解决一个几乎不存在的问题。

各位好，想麻烦帮忙评估一个数据接口的事。

先说下背景：乌干达分部现在有个自己在用的选址调查小工具，用户就十几个人，没有服务器也没有专门运维，就是个内部工具。大概是这么回事：调查员用一个 HTML 表单填选址调查，支持断网先填、联网再交，数据存在 Google Sheets 里，配了点 Apps Script 做轻量后端。另外有个从表格数据自动生成的地图看板，标出各个点位的位置和实拍照片，分部同事平时就点开这个看。数据量不大，几十个点位的规模。

现在想在这个基础上加一层店面管理，思路是这样：位置和选址调查还是我们自己管；店面基本信息（名称、地址、面积、负责人、营业状态这些）在现有系统里加；至于店面的经营数据（销售、库存这些）和监控画面，如果总部系统里已经有，我们就不想再建一套，直接调总部的 API 拿来展示就行。总之一句话：公司已有的数据，以总部为准，我们只做只读展示，不在自己这边再维护一份。后面换电站管理可能也复用这套架构，所以接口方案最好能通用一些。

想请教几个问题：

1. 公司现有系统（ERP、POS、CRM、监控这些）里，哪些数据能通过 API 提供给海外分部？
2. 如果能开放，安全和权限上推荐怎么做（API Key、JWT、OAuth、网关、VPN 之类）？有一点想先确认：我们的系统和人都在乌干达，总部有些系统是不是海外根本访问不到？
3. 调用量很小，十几个人只读查询，几分钟刷一次，安全评估按这个量级来就行。
4. 公司有没有现成的「海外分部调总部数据」的接口规范和申请流程？如果还没有现成 API，申请开发的流程和大致周期是怎样的？
5. 另外如果公司目前正在设计统一的数据管理系统，我们希望提前预留标准的数据接口，未来海外分部的小型业务系统可以通过 API 按权限调用相关数据。
6. 还有一件事想一并确认：我们这个内部工具打算用 Supabase 这类第三方云数据库做底座，公司对海外分部用这类服务有没有安全合规上的要求？如果以后要接总部数据，公司是否允许海外系统作为独立的小系统、按权限通过 API 调总部数据？
7. 还有一种情况想提前打听：如果有的系统有接口、但只能在内网用，公司有没有统一的 API 网关或者中间服务，让我们海外系统走公网 HTTPS 安全地调？
